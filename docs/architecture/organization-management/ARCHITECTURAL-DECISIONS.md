## ADR-001 — مالکیت چرخهٔ حیات سازمان، شعبه و عضویت‌ها در Organization Management

**وضعیت:** پذیرفته‌شده (هم‌راستا با مرزبندی معماری مصوب Access Control)  
**تاریخ مبنا:** ۱۴۰۵/۰۸/۱۱

### زمینه

Identity Access، Organization Management و Access Control مسئولیت‌های متفاوتی دارند. نبود مالکیت روشن باعث وابستگی دوری، نوشتن مستقیم روی جدول‌های Context دیگر و اختلاف در قواعد کسب‌وکار می‌شود.

### تصمیم

Organization Management مالک چرخهٔ حیات این مدل‌ها است:

- \`Organization\`
- \`Branch\`
- \`OrganizationMembership\`
- \`BranchMembership\`

Identity Access مالک User و احراز هویت است. Access Control مالک Role، Permission، RoleAssignment، Override و ارزیابی دسترسی است.

### پیامدها

- فقط Use Caseهای این Context مجاز به تغییر وضعیت چهار مدل فوق هستند.
- Contextهای دیگر فقط از طریق قرارداد یا Read Adapter محدود اطلاعات می‌خوانند.
- Import کردن Entityهای Domain این Context در Context دیگر ممنوع است.
- Migration و FK مشترک، مالکیت Domain را تغییر نمی‌دهد.

## ADR-002 — یک User می‌تواند عضو چند Organization باشد

**وضعیت:** پذیرفته‌شده (تصمیم مصوب Access Control، ADR-002)  
**تاریخ مبنا:** ۱۴۰۵/۰۸/۱۰

### زمینه

یک شخص ممکن است هم‌زمان با چند کسب‌وکار همکاری کند و در هر سازمان نقش و دسترسی متفاوتی داشته باشد.

### تصمیم

برای هر عضویت، یک \`OrganizationMembership\` مستقل میان User و Organization نگهداری می‌شود. هر عملیات و پرس‌وجوی سازمانی باید سازمان مقصد را صریح مشخص کند.

### پیامدها

- مجوز و دادهٔ یک سازمان نباید به سازمان دیگر نشت کند.
- عضویت با User Account یکی نیست.
- مدل فعلی برای زوج \`(organizationId, userId)\` قید یکتایی دارد.
- تست‌های امنیتی باید حداقل دو سازمان مستقل و یک User مشترک را پوشش دهند.

## ADR-003 — Organization و Branch ریشه‌های Aggregate مستقل باشند

**وضعیت:** پیشنهادی — در انتظار تأیید  
**تاریخ:** ۱۴۰۵/۰۸/۱۷

### زمینه

تعداد شعبه‌ها و اعضا می‌تواند با رشد کسب‌وکار افزایش یابد. نگهداری همهٔ شعبه‌ها و عضویت‌ها در Aggregate سازمان، بارگذاری و قفل‌گذاری غیرضروری ایجاد می‌کند.

### تصمیم پیشنهادی

\`Organization\` و \`Branch\` Aggregate Rootهای مستقل باشند. Branch فقط شناسهٔ سازمان مالک را نگهداری کند و قواعد رابطه از طریق Application و Constraintهای دیتابیس تضمین شوند. دو نوع Membership نیز Aggregate مستقل با شناسه‌های مرجع باشند.

### پیامدها

- عملیات شعبه برای تغییرات محلی، نیازمند بارگذاری تمام Organization نیست.
- مالکیت Branch از طریق \`organizationId\` کنترل می‌شود.
- قواعد چند Aggregate در Application orchestration می‌شوند، نه با دست‌کاری مستقیم Entityهای یکدیگر.
- این تصمیم باید پیش از ایجاد Repositoryهای کامل تأیید شود.

## ADR-004 — Membership یک مدل کسب‌وکاری مستقل از User است

**وضعیت:** پیشنهادی — در انتظار تأیید  
**تاریخ:** ۱۴۰۵/۰۸/۱۷

### زمینه

وضعیت همکاری کاربر با یک سازمان یا شعبه با وضعیت حساب کاربری او متفاوت است. یک User ممکن است حساب فعال داشته باشد اما در یک سازمان عضو نباشد، یا عضویتش در سازمانی تعلیق شده باشد.

### تصمیم پیشنهادی

دو مدل مستقل نگهداری شوند:

- \`OrganizationMembership\`: رابطهٔ User و Organization؛
- \`BranchMembership\`: رابطهٔ OrganizationMembership و Branch.

وضعیت User فقط در Identity Access باقی بماند. این Context فقط وضعیت همکاری/عضویت را کنترل کند.

### پیامدها

- تعلیق عضویت، حساب User را تعلیق نمی‌کند.
- حذف User و عضویت، دو مفهوم متفاوت‌اند.
- تغییرات عضویت باید Use Case و مجوز مستقل داشته باشند.
- یک BranchMembership بدون OrganizationMembership معتبر قابل ایجاد نیست.

## ADR-005 — BranchMembership باید به Branch و OrganizationMembership هم‌ساز متصل باشد

**وضعیت:** پیشنهادی — در انتظار تأیید  
**تاریخ:** ۱۴۰۵/۰۸/۱۷

### زمینه

صرف معتبر بودن شناسهٔ Branch و Membership کافی نیست؛ ممکن است هرکدام به دو Organization متفاوت تعلق داشته باشند.

### تصمیم پیشنهادی

برای ایجاد BranchMembership باید:

1. OrganizationMembership معتبر باشد؛
2. سازمان آن فعال باشد؛
3. Branch فعال باشد؛
4. Branch و OrganizationMembership متعلق به یک سازمان باشند.

قیدهای مرکب FK در Schema فعلی برای کنترل تعلق مشترک وجود دارند و Application نیز باید همان قاعده را پیش از نوشتن اعتبارسنجی کند.

### پیامدها

- شناسه‌های ارسالی از Client قابل اعتماد تلقی نمی‌شوند.
- تست Integration باید تلاش برای اتصال عضو سازمان A به شعبهٔ سازمان B را رد کند.
- BranchMembership نباید عضویت سازمانی جدید ایجاد یا جایگزین کند.

## ADR-006 — وضعیت سازمان، شعبه و عضویت معانی جداگانه دارند

**وضعیت:** پیشنهادی — در انتظار تأیید  
**تاریخ:** ۱۴۰۵/۰۸/۱۷

### زمینه

مدل فعلی سه نوع وضعیت با معنای متفاوت دارد:

- Organization: \`ACTIVE | SUSPENDED\`
- Branch: \`ACTIVE | INACTIVE\`
- Membership: \`INVITED | ACTIVE | SUSPENDED | REMOVED\`

استفاده از یک Status عمومی یا تغییر هم‌زمان وضعیت همهٔ فرزندان، معنای چرخهٔ حیات را مبهم می‌کند.

### تصمیم پیشنهادی

Enumهای فعلی از هم مستقل باقی بمانند. هر Entity فقط وضعیت خودش را تغییر دهد. Transitionها در Use Caseهای مشخص تعریف و آزمون شوند. \`REMOVED\` از مسیر ویرایش عمومی به \`ACTIVE\` برنگردد.

### پیامدها

- تغییر وضعیت باید idempotent و دارای نتیجهٔ مشخص باشد.
- وضعیت سازمان نباید با تغییر وضعیت تک‌تک Branchها شبیه‌سازی شود.
- سیاست دعوت مجدد یا دورهٔ عضویت جدید نیازمند تصمیم جداگانه است.

---

## ADR-007 — تعلیق سازمان و شعبه وضعیت فرزندان را به‌صورت خودکار بازنویسی نمی‌کند

**وضعیت:** پیشنهادی — در انتظار تأیید  
**تاریخ:** ۱۴۰۵/۰۸/۱۷

### زمینه

تغییر Status تمام شعبه‌ها و عضویت‌ها هنگام Suspend کردن سازمان، تغییرات حجیم و برگشت‌ناپذیر یا دشوار برای بازگردانی ایجاد می‌کند.

### تصمیم پیشنهادی

تعلیق Organization یک شرط سراسری دسترس‌پذیری است؛ وضعیت Branch و Membership مستقل حفظ می‌شود. تعلیق Branch نیز فقط دسترسی به همان Branch را متوقف می‌کند و Membershipها را تغییر نمی‌دهد.

### پیامدها

- با فعال‌سازی دوبارهٔ سازمان/شعبه، وضعیت مستقل قبلی فرزندان حفظ می‌شود.
- Access Control باید وضعیت جاری Organization و Branch را در تصمیم دسترسی بررسی کند.
- وضعیت عضویت سازمانی و شعبه‌ای به‌صورت مستقل ارزیابی می‌شود.
- قاعدهٔ ارث‌بری Permission از Role سازمانی باید با ADR-007 در Access Control هم‌راستا بماند: غیرفعال بودن BranchMembership به‌تنهایی مجوز ارث‌رسیده از Role سازمانی را باطل نمی‌کند.

## ADR-008 — در v1 حذف فیزیکی Organization، Branch و Membership ارائه نشود

**وضعیت:** پیشنهادی — در انتظار تأیید  
**تاریخ:** ۱۴۰۵/۰۸/۱۷

### زمینه

رکوردهای سازمانی به عضویت، نقش، Audit و داده‌های Contextهای دیگر مرجع می‌دهند. حذف فیزیکی می‌تواند تاریخچه یا روابط وابسته را از بین ببرد. Schema فعلی در چند رابطه از \`onDelete: Cascade\` استفاده می‌کند.

### تصمیم پیشنهادی

چرخهٔ حیات با Suspend، Inactive و Removed مدیریت شود. تا زمان تصویب Retention و رفتار حذف، Use Case حذف فیزیکی ساخته نشود. پیش از فعال کردن حذف فیزیکی، FKهای Cascade و اثر آن‌ها روی Access Control و سایر Contextها بازبینی شوند.

### پیامدها

- تاریخچه به‌صورت پیش‌فرض از بین نمی‌رود.
- تغییر Schema باید با Migration رو به جلو و بررسی سازگاری انجام شود.
- این تصمیم به معنی ادعای Append-only بودن تمام داده‌های این Context نیست؛ سیاست Audit باید جداگانه تعیین شود.

## ADR-009 — مالک سازمان Workflow اختصاصی و هماهنگ با Access Control دارد

**وضعیت:** پیشنهادی — در انتظار تأیید  
**تاریخ:** ۱۴۰۵/۰۸/۱۷

### زمینه

\`Organization.ownerUserId\` در Organization Management قرار دارد، در حالی که نقش سیستمی \`ORGANIZATION_OWNER\` و RoleAssignment متعلق به Access Control است. تغییر یکی بدون دیگری باعث ناسازگاری مالکیت و دسترسی می‌شود.

### تصمیم پیشنهادی

- مالک اولیه باید User معتبر و دارای OrganizationMembership فعال باشد.
- تغییر یا حذف عضویت مالک فعلی بدون انتقال مالکیت مجاز نیست.
- ایجاد سازمان و انتقال مالکیت فقط از Workflow اختصاصی انجام شوند.
- Workflow باید تغییر \`ownerUserId\` و RoleAssignment متناظر را با تضمین اتمی یا سیاست سازگاری جبرانی مصوب هماهنگ کند.
- Generic Role Assignment نباید جایگزین Workflow مالکیت شود.

### پیامدها

- Organization Management فقط مالکیت سازمان را تغییر می‌دهد.
- Access Control فقط نقش و تخصیص آن را تغییر می‌دهد.
- Orchestrator باید از قراردادهای عمومی دو Context استفاده کند، نه Repository یا Entity داخلی آن‌ها.
- پیش از توسعهٔ Owner workflow، مرز Transaction بین Contextها باید مشخص شود.

## ADR-010 — Identity Access مرجع قطعی وضعیت User است

**وضعیت:** پذیرفته‌شده (هم‌راستا با معماری مصوب Identity Access)  
**تاریخ مبنا:** ۱۴۰۵/۰۸/۱۱

### زمینه

Organization Management به شناسه و وضعیت User نیاز دارد، اما نباید مالک داده‌های هویتی یا احراز هویت شود.

### تصمیم

این Context فقط User ID را نگهداری و برای نیازهای خود وضعیت User را از قرارداد Identity Access دریافت می‌کند. تغییر User status، Credential و Session خارج از مسئولیت آن است.

### پیامدها

- Domain این Context نباید به User Entity خارجی وابسته باشد.
- Port حداقلی مانند User existence/status lookup کافی است.
- دادهٔ Identity در مدل محلی کپی دائمی نشود.
- خطای وابستگی Identity هنگام تصمیم حساس باید Fail closed باشد.

## ADR-011 — Access Control تنها مرجع تصمیم مجوز است

**وضعیت:** پذیرفته‌شده (هم‌راستا با معماری مصوب Access Control)  
**تاریخ مبنا:** ۱۴۰۵/۰۸/۱۱

### زمینه

Permission Registry، Roleها، Delegation و ارزیابی دسترسی در Access Control قرار دارند. تکرار این منطق در Organization Management به دو منبع تصمیم منجر می‌شود.

### تصمیم

Application Use Caseهای Organization Management از Authorization Port برای ارزیابی عملیات استفاده می‌کنند. این Context Permission را محاسبه یا Role را تفسیر نمی‌کند.

### پیامدها

- Guard HTTP به‌تنهایی کافی نیست؛ Use Case حساس نیز مرز مجوز را محافظت می‌کند.
- در Access Control اختلال باشد، عملیات حساس اجرا نمی‌شود.
- Adapter مجوزدهی به API/Port عمومی وابسته است، نه Domain داخلی Access Control.
- تغییر Role یا Permission در Organization Management ممنوع است.

## ADR-012 — استفاده از Read Adapter مشترک در Modular Monolith مجاز، اما محدود است

**وضعیت:** پیشنهادی — در انتظار تأیید  
**تاریخ:** ۱۴۰۵/۰۸/۱۷

### زمینه

چند Context به facts مشترکی مانند User status، Organization status و Membership status نیاز دارند. در Modular Monolith فعلی، دیتابیس مشترک است؛ با این حال وابستگی مستقیم به مدل Domain Context دیگر مرزها را تضعیف می‌کند.

### تصمیم پیشنهادی

در صورت نیاز، Adapter زیرساختی می‌تواند با Prisma مشترک Read Model محدودی بخواند، اما قرارداد آن در لایهٔ Application تعریف شود و Domain Context دیگر را Import نکند. نوشتن دادهٔ Context دیگر از این مسیر ممنوع است.

### پیامدها

- وابستگی در زمان اجرا صریح و یک‌طرفه می‌ماند.
- Nest Moduleها نباید Circular Dependency داشته باشند.
- انتقال آینده به سرویس مستقل آسان‌تر خواهد بود، بدون آنکه اکنون Microservice معرفی شود.

## ADR-013 — معنای دعوت و عضویت مجدد نیازمند تصمیم محصولی است

**وضعیت:** پیشنهادی — در انتظار تأیید  
**تاریخ:** ۱۴۰۵/۰۸/۱۷

### زمینه

Schema فعلی \`userId\` را در OrganizationMembership اجباری می‌کند و برای هر زوج Organization/User یک رکورد می‌پذیرد؛ در عین حال Status برابر \`INVITED\` دارد. بنابراین دعوت شخصی که هنوز User ندارد، با مدل موجود به‌صورت مستقل نمایش داده نمی‌شود.

### تصمیم پیشنهادی برای v1

تا زمان طراحی موجودیت Invitation، فقط User موجود از طریق شناسهٔ User می‌تواند وارد فرآیند عضویت شود. دعوت مبتنی بر ایمیل برای شخص فاقد حساب، نیازمند مدل و Workflow مستقل است؛ Outbound Email صرفاً ارسال‌کننده است و مالک دعوت نیست.

سیاست بازگشت از \`REMOVED\` و نیاز به چند دورهٔ عضویت نیز باید روشن شود. قید یکتایی فعلی اجازهٔ ساخت دوره‌های متعدد برای همان رابطه را نمی‌دهد.

### پیامدها

- مفهوم «عضویت دعوت‌شده» با «دعوت‌نامهٔ ایمیلی پیش از ساخت User» اشتباه نمی‌شود.
- تغییر قیدهای یکتا یا افزودن Invitation بدون ADR و Migration انجام نمی‌شود.
- Email delivery به‌تنهایی عضویت را فعال نمی‌کند.

## ADR-014 — از پیچیدگی غیرضروری در نسخهٔ اول اجتناب شود

**وضعیت:** پیشنهادی — در انتظار تأیید  
**تاریخ:** ۱۴۰۵/۰۸/۱۷

### زمینه

نیاز فعلی، یک Modular Monolith با مرزهای دامنهٔ قابل فهم است؛ معماری عمومی برای همهٔ انواع سازمان و ساختارهای نامحدود لازم نیست.

### تصمیم پیشنهادی

در v1 بدون نیاز و تأیید صریح، موارد زیر اضافه نشوند:

- Hierarchy عمومی برای Organization یا Branch؛
- موتور Policy یا ABAC عمومی؛
- Event Sourcing؛
- Microservice یا Message Broker جدید؛
- Cache دائمی برای وضعیت عضویت/مجوز؛
- Generic Repository و Generic CRUD framework؛
- Workflow builder یا State machine framework عمومی.

### پیامدها

هر Abstraction باید مصرف‌کننده و Invariant واقعی داشته باشد. پیچیدگی آینده با ADR مستقل و بر اساس نیاز واقعی وارد می‌شود.
